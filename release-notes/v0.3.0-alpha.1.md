**Alpha release preparation — not yet published.** The `v0.3.0-alpha.1` naming and alpha direction have been approved. This is the third planned GitHub release, following LibreDash v0.1.0 and LeapView v0.2.0-rc.1. Features remain under active development and interfaces may change incompatibly. The repository version files are aligned; publication remains gated on qualification of the exact release artifacts.

Research cutoff: 24 September 2026, main commit [`499af82d0586df79ddd647b72b2c5b25500d59d8`](https://github.com/flidai/leapview/commit/499af82d0586df79ddd647b72b2c5b25500d59d8). This proposed LeapView alpha brings local-first analytics development, an interactive dashboard builder, a four-page CFO example, and a PostgreSQL-backed operational architecture. It also refines dashboard navigation, charts, tables, chat, and administration.

**Alpha status:** features are still under development, interfaces may change incompatibly, and workflows may be incomplete. This build is intended for controlled testing and feedback, not production reliance or final-release promotion. Alpha labeling does not waive required build, security, or qualification checks. **Read the compatibility section before using existing state or projects.**

## Highlights

### Develop analytics locally, then deliver a reviewed project

- Initialize a project with the native `leapview` authoring CLI and work through a local development lifecycle with a version-matched runtime.
- Use explicit development connection profiles, isolated checkout-owned resources, and authenticated private previews. Preview handling retains the last valid project and rejects stale responses.
- Prepare and resume delivery operations while preserving source identity and target authorization boundaries.
- Local Docker support covers Linux and recognized macOS Docker Engine providers, with follow-up fixes for first-run bootstrap and local authentication.

Sources: [#636](https://github.com/flidai/leapview/pull/636), [#676](https://github.com/flidai/leapview/pull/676), [#681](https://github.com/flidai/leapview/pull/681), [#690](https://github.com/flidai/leapview/pull/690).

### Build dashboards visually while keeping dashboard code authoritative

- Create private dashboard copies and edit them with Build and Format inspectors, governed semantic fields, filters, interactions, and undo/redo.
- Arrange visuals with drag, resize, and keyboard placement, with page settings and interactive previews.
- Browse repository-managed and UI-authored dashboards through catalog views and ownership metadata.
- Follow-up fixes improve copying, private-draft deletion with confirmation and authorization, builder streams, navigation, scrolling, table loading, and chart presentation. These are specific improvements, not a claim that all builder issues are resolved.

Sources: [#377](https://github.com/flidai/leapview/pull/377), [#589](https://github.com/flidai/leapview/pull/589), [#686](https://github.com/flidai/leapview/pull/686), [#689](https://github.com/flidai/leapview/pull/689), [#691](https://github.com/flidai/leapview/pull/691), [#694](https://github.com/flidai/leapview/pull/694).

### Explore the CFO Command Center example

The repository includes Overview, Statement, Liquidity, and Drivers pages built from Microsoft's public Financial Sample workbook, with linked filtering and financial presentation improvements. Budget, forecast, operating-expense, EBITDA, variance-driver, and cash figures include **deterministic fictional planning scenarios**, not real company forecasts. Hosted-demo publication now supports the CFO dataset.

Sources: [#559](https://github.com/flidai/leapview/pull/559), [#600](https://github.com/flidai/leapview/pull/600), [#683](https://github.com/flidai/leapview/pull/683).

### Refined navigation, chat, and administration

- Insights and Develop organize viewing and authoring workflows; catalog, sidebar, branding, account settings, and dashboard-page navigation receive refinements.
- Chat improvements cover discovery, rename/delete menus, archive access, conversation controls, and recovery from interrupted page streams.
- Agent configuration supports deployment-managed live reload: valid changes apply to new requests while active requests retain their captured configuration; invalid updates retain the last known-good configuration.
- The built-in OpenAI-compatible provider defaults to GPT-6 Luna and uses the Responses API for GPT-6 Luna models. Other configured models continue to use the Chat Completions API. Agent use still requires operator configuration and provider credentials; this does not include model access or usage credits.

## Data contracts and access control

- Portable source roots use Connections, Sources, Models, SemanticModels, Pipelines, and Dashboards. Project identity is bound at the target rather than selected through browser routes or embedded in a portable project resource.
- Source and Model declarations share `spec.fields` and `spec.checks`. Source checks validate captured inputs; Model checks validate transformed outputs.
- Semantic authoring places metrics beside their datasets. Identifiable authored definitions use named lists with duplicate-identity validation.
- Semantic access changes enforce authorization through discovery, planning, and cache boundaries. Target-owned grants allow dashboard access without granting a broad project role.
- dbt integration consumes published physical relations or Parquet through ordinary LeapView resources; dbt remains the transformation engine. ODCS export and OpenLineage projections add interoperability without replacing LeapView's authoritative contracts.

## Operations and reliability

- PostgreSQL 18 becomes the durable control and coordination store, with a separate PostgreSQL-backed DuckLake catalog. DuckDB remains the analytical execution engine; managed objects remain in their configured storage.
- River handles operational job execution while LeapView retains its product job identities, history, and authorization.
- Recovery work adds durable evidence, transition qualification, coordinated provider restore, and replacement-host admission. Provider operations and topology-specific qualification remain required.
- Debian 13 joins the supported generic VPS bootstrap path, including Docker CLI installation fixes.
- Chart formatting, large-table scrolling, page-stream recovery, cache identity, audit diagnostics, and dashboard latency monitoring receive fixes and expanded coverage. No numerical performance improvement is claimed here.
- The repository is now licensed under Apache-2.0.

## Compatibility and upgrade considerations

**This is a substantial architecture and authoring-contract change from rc.1, not a routine image replacement.**

1. **Do not assume an in-place upgrade from rc.1.** Current PostgreSQL-era transition preflight explicitly excludes SQLite-era predecessors. Preserve the old installation and its recovery material. Use a separately provisioned target for evaluation; any state transfer needs its own supported, rehearsed plan. This draft does not certify a migration from rc.1.
2. **Provision production PostgreSQL explicitly.** The production Compose bundle does not provision the database service. Configure separate control/DuckLake roles, authenticated TLS (`verify-full`), pool identities, and provider-managed recovery. Serving startup verifies schemas; it must not silently apply pending migrations.
3. **Migrate authored definitions.** Legacy keyed-map aliases are not retained by the named-list change. Review Source/Model fields and checks, explicit `non_null` rules, dataset-local metrics, resource names, and target-bound Project identity. Validate and qualify projects before activation.
4. **Do not reuse obsolete operations commands from the rc.1 notes.** The current `leapviewctl` command surface does not provide the old generic `backup`, `restore`, `upgrade`, or `rollback` commands. Recovery uses provider-native PostgreSQL and managed-data procedures. Returning to an old image does not undo database migrations.
5. **Historical PostgreSQL revision 23 has two known lineages.** Migration 024 converges them forward; the reviewed snapshot also includes migrations through 028. A revision number alone is insufficient to establish a supported transition. This convergence is not an rc.1 SQLite migration.
6. **Check package types and platforms.** The current release workflow targets Linux AMD64/ARM64 runtime container images. Both Compose operations archives and authoring CLI archives are packaged for Linux and macOS, on AMD64 and ARM64. Desktop installers have a separate release workflow and are not promised as assets of this server release.

References at the reviewed source: [upgrade guide](https://github.com/flidai/leapview/blob/499af82d0586df79ddd647b72b2c5b25500d59d8/docs/articles/operate/upgrades.md), [Compose guide](https://github.com/flidai/leapview/blob/499af82d0586df79ddd647b72b2c5b25500d59d8/deploy/compose/README.md), [recovery guide](https://github.com/flidai/leapview/blob/499af82d0586df79ddd647b72b2c5b25500d59d8/docs/articles/operate/backup-restore.md), [#666](https://github.com/flidai/leapview/pull/666).

- The dbt guide distinguishes proven local execution from live Azure qualification; a reference workflow alone is not live Azure evidence.
- Local password authentication is not MFA. Use an external identity provider when MFA is required.
- The saved-exploration feature in #543 was reverted by #569 and is not advertised as delivered in these notes.
